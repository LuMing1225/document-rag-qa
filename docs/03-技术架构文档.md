## 2. 模块划分和职责

### 2.1 backend/ 后端模块

| 模块 | 职责 |
|------|------|
| `main.py` | FastAPI应用入口，路由注册，CORS配置 |
| `pdf_parser.py` | PDF加载、文本块提取、表格识别 |
| `layout_analyzer.py` | 双栏检测、标题层级识别、阅读顺序排序 |
| `chunker.py` | 父子分块、重叠控制、表格保护 |
| `embedding.py` | 调用Ollama bge-m3生成向量嵌入 |
| `vector_store.py` | FAISS索引管理、向量存取、ANN检索 |
| `reranker.py` | BGE-Reranker重排序（CrossEncoder） |
| `generator.py` | 调用Ollama qwen3:8b生成回答 |
| `schemas.py` | Pydantic数据模型定义 |

### 2.2 frontend/ 前端模块

| 模块 | 职责 |
|------|------|
| `app.py` | Streamlit主入口，页面路由 |
| `pages/upload.py` | PDF上传页面 |
| `pages/layout_view.py` | 版面分析可视化 |
| `pages/chat.py` | 问答交互页面 |
| `pages/index_mgmt.py` | 知识库索引管理 |

## 4. 数据流

完整数据流如下：

```
PDF文件
  → pdfplumber解析（提取文本块+坐标+表格）
  → 版面分析引擎（双栏检测→阅读顺序重排→标题层级识别）
  → 父子分块引擎
      ├─ 父文档切分（按章节边界，~1200 tokens）
      └─ 子文档切分（父文档内滑动窗口，~300 tokens，50 tokens重叠）
  → 嵌入生成
      └─ 子文档文本 → Ollama bge-m3 → 1024维稠密向量
  → FAISS索引构建
      └─ IndexHNSWFlat(1024) 存入子向量
  → 检索阶段
      Query → bge-m3嵌入 → FAISS ANN检索(top-20子文档)
      → 去重得到父文档列表
      → BGE-Reranker对Query-Parent对重排(top-5)
      → 拼接父文档上下文
      → qwen3:8b生成回答
```

## 5. 多向量检索评分公式推导

### 5.1 公式

$$Score_{final} = \beta \cdot Sim_{Dense}(Query, Child) + (1-\beta) \cdot Sim_{Rerank}(Query, Parent)$$

其中：
- **β**：稠密检索权重系数，默认0.3
- **Sim_Dense(Query, Child)**：Query与子文档的余弦相似度（FAISS返回，范围[-1,1]）
- **Sim_Rerank(Query, Parent)**：Query与父文档的CrossEncoder重排分数（BGE-Reranker输出，范围[0,1]）

### 5.2 为什么是混合评分

1. **Dense检索的优势**：子文档小，语义聚焦，向量召回快（FAISS ANN毫秒级）
2. **Dense检索的劣势**：只看子文档，缺少上下文，可能召回"看起来相关但实际不完整"的片段
3. **Reranker的优势**：CrossEncoder同时编码Query和Parent，能理解完整语境，判断真正相关性
4. **Reranker的劣势**：计算量大，不能对全部百万级向量做CrossEncoder，只能对top-N做

### 5.3 β参数选择

- β=0.5：等权，适合通用场景
- β=0.3：偏重重排结果，适合对精度要求高的医疗场景（本项目默认）
- β=0.7：偏重稠密检索速度，适合对延迟敏感的场景

## 6. 8GB显存管理策略

在8GB显存（如RTX 3070/4060级别）上运行本系统的显存分配：

| 组件 | 显存占用 | 管理策略 |
|------|----------|----------|
| bge-m3嵌入模型 | ~1.5GB | 常驻GPU，batch_size=32 |
| BGE-Reranker-Large | ~2.0GB | 按需加载，检索时加载，空闲时卸载到CPU |
| qwen3:8b (Ollama) | ~5.0GB | Ollama自动管理，`num_gpu`参数控制层数 |
| FAISS索引 | 不占显存 | 纯CPU内存检索，ANN在内存中运行 |

**关键策略**：
1. **嵌入模型常驻**：bge-m3小而频繁使用，常驻GPU
2. **Reranker动态加载**：检索时从CPU加载到GPU，检索完卸载
3. **LLM交给Ollama管理**：Ollama有自己的显存调度，会自动卸载不常用模型
4. **batch控制**：嵌入生成batch_size≤32，避免OOM
5. **CPU回退**：如果显存不足，嵌入计算自动回退到CPU（速度慢但可用）
