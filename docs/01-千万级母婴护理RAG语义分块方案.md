# 千万级母婴护理RAG语义分块方案

## 1. 项目背景

本项目服务于母婴护理连锁机构集团知识库场景。该集团在全国拥有数百家月子中心和母婴护理站点，累计积累了超过 **1000万页** 的PDF文档资料，包括：

- **护理操作手册**：新生儿抚触、 bath time、脐部护理等SOP流程文档
- **喂养指南**：母乳喂养、配方奶喂养、辅食添加等营养指导
- **疾病预案**：黄疸筛查、发热处理、窒息急救等临床应急方案
- **体温监测记录**：婴儿每日体温日志、光疗监测表等结构化表格
- **培训教材**：护理员岗前培训、复训考核资料
- **制度文件**：集团质量管理规范、感染控制标准

这些文档总量超过 **500GB**，涵盖双栏排版的技术手册、跨页连续的监测表格、图文混排的操作指南等复杂版面。传统的固定长度分块（如512 tokens硬切）会导致：

1. **表格被截断**：体温监测表格跨页时被切分到两个chunk，丢失行对应关系
2. **双栏阅读顺序错乱**：左栏末尾和右栏开头被拼接到一起，语义断裂
3. **标题与正文分离**：章节标题被切到上一个chunk末尾，正文chunk缺少上下文
4. **父子上下文丢失**：检索到一个300字的小段落，但LLM需要其父章节的完整背景才能正确回答

因此，本项目采用 **版面分析驱动的父子分块（Parent-Child Chunking）** 方案，在千万级文档规模下实现高精度语义检索。

---

## 2. 复杂版面挑战

### 2.1 双栏排版

母婴护理培训教材大量采用双栏排版（类似杂志版式），目的是在有限页面内容纳更多图文内容。直接按坐标从上到下、从左到右提取文本会得到错误的阅读顺序：

```
错误提取顺序：
  [左栏标题] [右栏标题]
  [左栏正文第1行] [右栏正文第1行]
  [左栏正文第2行] [右栏正文第2行]
```

这会导致左右两栏内容交叉混杂，语义完全错乱。

### 2.2 体温监测表格

体温监测记录是典型的跨页表格，包含日期、时间、体温值、喂奶量、排便情况等多列。在PDF中：

- 表头可能重复出现在每页顶部
- 表格跨页时，最后一行可能被截断
- 单元格内可能包含多行备注文字
- 合并单元格导致列对齐关系复杂

### 2.3 跨页列表

疫苗接种计划、辅食添加原则等内容常以项目符号列表形式跨页延续。如果按页切分，列表项会被截断，导致检索结果不完整。

## 3. 版面分析架构

### 3.1 业界方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| Layout-Parser | 基于目标检测模型（如Mask R-CNN）识别版面元素 | 精度高，支持自定义标注 | 需GPU推理，部署复杂 |
| DocLayout-YOLO | 基于YOLOv8的版面分析专用模型 | 速度快，精度高 | 需要预训练权重 |
| PyMuPDF坐标提取 | 基于PDF自带的文本块坐标 | 无需模型，速度极快 | 对复杂版面支持有限 |
| pdfplumber | 基于PDF文本流+表格检测 | 表格识别好 | 无版面语义理解 |

### 3.2 本项目方案：坐标启发式版面分析

考虑到部署成本和8GB显存限制，本项目采用 **pdfplumber坐标启发式** 方案，不依赖深度学习版面模型：

1. **文本块提取**：用pdfplumber提取每个文本块的 bounding box（x0, top, x1, bottom）
2. **双栏检测**：统计页面文本块的x坐标分布，如果存在明显的双峰分布（左侧密集区+右侧密集区），判定为双栏
3. **表格检测**：用pdfplumber的`extract_tables()`识别表格区域，表格区域内的文本块标记为`table`类型
4. **标题层级识别**：根据字体大小、加粗、位置等特征推断标题级别（H1/H2/H3）
5. **阅读顺序排序**：单栏按top坐标排序；双栏先按column分组（左栏全部内容先排，再排右栏），栏内按top排序

### 3.3 双栏阅读顺序拼接算法

```python
def detect_and_order_columns(page_text_blocks, page_width):
    """
    双栏检测与阅读顺序重排
    输入: page_text_blocks = [{bbox, text, font_size, ...}, ...]
    输出: 按正确阅读顺序排列的文本块列表
    """
    mid_x = page_width / 2

    # 统计左半区和右半区的文本块数量
    left_blocks = [b for b in page_text_blocks if b['bbox'][0] < mid_x]
    right_blocks = [b for b in page_text_blocks if b['bbox'][0] >= mid_x]

    # 如果左栏和右栏都有足够内容，则判定为双栏
    is_double_column = len(left_blocks) > 3 and len(right_blocks) > 3

    if is_double_column:
        # 左栏按top坐标排序，右栏按top坐标排序
        left_sorted = sorted(left_blocks, key=lambda b: b['bbox'][1])
        right_sorted = sorted(right_blocks, key=lambda b: b['bbox'][1])
        return left_sorted + right_sorted  # 先左栏全部，再右栏全部
    else:
        # 单栏：按top坐标排序，top相近时按x坐标排序
        return sorted(page_text_blocks, key=lambda b: (b['bbox'][1], b['bbox'][0]))
```

## 4. 父子分块（Parent-Child Chunking）设计

### 4.1 为什么需要父子分块

传统RAG中，文档被切分为固定大小的chunk后直接做向量检索和上下文拼接。这存在一个根本矛盾：

- **chunk太小**：检索精度高（向量匹配更精准），但上下文不足，LLM无法理解完整语境
- **chunk太大**：上下文充足，但向量检索精度下降（一个chunk包含太多主题，向量被"稀释"），且浪费LLM上下文窗口

父子分块（也称为Small-to-Big Retrieval）解决了这个矛盾：

- **子文档（Child Chunk）**：小粒度（300 tokens），用于稠密向量检索，精度高
- **父文档（Parent Chunk）**：大粒度（1200 tokens），用于LLM上下文，信息完整
- **映射关系**：每个子文档指向其父文档ID，检索命中子文档后，返回父文档作为上下文

### 4.2 子文档300 tokens做稠密向量检索的原理

稠密向量检索的精度取决于query和document的语义重叠程度。当子文档大小为300 tokens（约200-250个中文字）时：

1. **主题单一**：每个子文档通常只讲一个知识点，向量表示更"纯粹"，与query的匹配更精准
2. **Embedding模型最优输入长度**：bge-m3等嵌入模型的最优输入长度通常在256-512 tokens之间，300 tokens正好落在甜区
3. **召回率高**：小chunk意味着更多的独立语义单元，query更容易命中相关段落

### 4.3 父文档1200 tokens用于LLM上下文的原理

检索到子文档后，我们不直接把子文档传给LLM，而是返回其父文档（1200 tokens）：

1. **上下文完整**：父文档包含子文档所在章节的完整内容，包括前后文的定义、背景、注意事项
2. **引用完整**：表格、列表等结构化内容不会被截断
3. **LLM理解充分**：1200 tokens约800-1000个中文字，足够LLM理解一个完整的知识点，且不会占用太多上下文窗口
4. **重排友好**：父文档作为整体参与重排序，CrossEncoder可以评估query与完整章节的相关性

## 5. 表格保留准则

### 5.1 表格转Markdown

表格内容必须转换为Markdown格式保留，不做自然语言切分：

```markdown
| 月龄 | 每日次数 | 单次奶量(ml) | 夜间喂养 |
|------|----------|-------------|----------|
| 0-1周 | 8-12次 | 10-30 | 2-3次 |
| 1-4周 | 8-10次 | 30-90 | 2次 |
```

### 5.2 不切分、独立成块

- 表格作为一个完整的父文档块存在，不按行切分
- 表格不拆分为子文档（因为表格行之间有依赖关系）
- 表格块的`layout_type`标记为`table`
- 表格块的向量嵌入使用Markdown文本直接编码

## 6. 分块参数选择依据

| 参数 | 值 | 选择依据 |
|------|-----|----------|
| 子文档大小 | 300 tokens | bge-m3最优输入长度甜区；主题单一性最佳；检索精度最高 |
| 父文档大小 | 1200 tokens | 一个完整小节的平均长度；LLM上下文效率最优；8K上下文窗口可容纳4-6个父文档 |
| 重叠大小 | 50 tokens | 避免边界语义断裂；占子文档的16.7%，平衡冗余和完整性 |
| 表格块大小 | 不限制 | 表格完整性优先，不做切分 |

为什么不是其他值？

- **子文档200 tokens**：太小，经常一句话不够一个完整语义单元，召回率下降
- **子文档500 tokens**：太大，向量开始"稀释"，检索精度下降
- **父文档800 tokens**：太小，章节上下文不完整，LLM可能断章取义
- **父文档2000 tokens**：太大，一个上下文窗口只能放3-4个父文档，且重排成本高

## 7. 元数据规范

每个chunk（无论父子）都携带以下元数据：

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| chunk_id | string | 全局唯一ID | "child_2024001_03" |
| parent_id | string | 父文档ID（子文档必填） | "parent_2024001" |
| page_number | int | 所在PDF页码 | 1 |
| position_tag | string | 位置标记：body/table/heading/list | "body" |
| layout_type | string | 版面类型：paragraph/table/list/figure | "table" |
| heading_path | string | 标题层级路径 | "第二章 > 2.1 新生儿黄疸" |
| column | string | 所在栏位：left/right/full | "left" |

这些元数据在检索时可用于：
- **过滤**：只检索`layout_type=table`的表格数据
- **提升**：标题路径匹配的chunk给予权重加成
- **展示**：前端展示时显示页码和章节路径
